# Identity and access-control constraints

Research date: 2026-09-04

This note gathers current, vendor-neutral constraints for identity, roles, collaboration, and administrative control in the managed AI OSINT Spider service. It uses federal guidance as a security design reference; citing an NIST assurance level does not claim that the product is certified or conforms to that assurance level. The accountless local application remains outside managed-cloud identity until a user signs in and migrates or creates a managed Case.

## Sourced constraints

### Authentication and recovery

NIST SP 800-63B-4 requires an AAL2 verifier to offer a phishing-resistant option. It also recommends that subscribers maintain at least two authentication methods, permits multiple authenticators per account, requires authentication before adding an authenticator, and requires an independent notification when one is added. Its AAL2 recovery pattern requires two different recovery methods, one recovery method plus an existing authenticator, or repeated identity proofing; every recovery event generates a notification. These are useful targets for a service holding sensitive investigation data, but they do not by themselves make the service AAL2-compliant. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

WebAuthn creates public-key credentials scoped to a relying party and origin. The authenticator retains the credential private key, and any biometric used for local user verification is not disclosed to the relying party. This supports passkeys without collecting biometric templates in the service. [W3C Web Authentication Level 2](https://www.w3.org/TR/webauthn-2/)

For installed and hybrid applications, OAuth native-app guidance requires an external user agent such as the system browser rather than an embedded webview. Public native clients use authorization code with PKCE; claimed HTTPS redirects are preferred where supported, while a temporary loopback listener is an established desktop option. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)

### Sessions, devices, and tokens

NIST requires session secrets to be generated by the session host, carried over an authenticated protected channel, invalidated on logout, and rejected after their time limit. It warns against placing browser session secrets in HTML local storage. OWASP calls for server-enforced idle and absolute timeouts, session renewal after a privilege change, reauthentication after recovery and other high-risk events, and user-visible controls to inspect and remotely terminate sessions. [NIST session management](https://pages.nist.gov/800-63-4/sp800-63b/session/), [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

OAuth access tokens should have only the necessary scope and audience. Public clients' refresh tokens must be rotated or sender-constrained, and refresh-token issuance and lifetime require a risk decision. Revocation may have a propagation delay; cached introspection results create a documented stale-authorization window and must not outlive a token's expiry. [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009.html), [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html)

Bearer credentials must be protected in transit and must not be placed in page URLs, where browser history, referrers, and logs can expose them. Security logs should also omit raw session identifiers and access tokens. [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html), [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### Tenant and Case authorization

Authorization should enforce least privilege, deny by default, and check the particular object and operation on every request. Static files and object storage require the same authorization boundary as records; a hard-to-guess identifier is not authorization, and client-side checks cannot be decisive. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

In a multi-tenant service, client-supplied tenant identifiers are selectors only. Tenant context must be derived from a verified identity and current membership, propagated to every storage, cache, queue, asynchronous job, search, and object path, and re-established for each transaction. Cross-tenant negative-path tests are required because shared infrastructure can leak through more than the primary database. [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)

NIST SP 800-53 calls for least privilege, separation of duties, restricted privileged functions, auditing of privileged actions, and separation between access-control administration and audit administration when the risk warrants it. These controls support distinct organization, Case, billing, audit, and service-support authority rather than one universal administrator role. [NIST SP 800-53 Rev. 5.2.0](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)

### Invitations, administration, audit, and sharing

OWASP's recovery-link guidance requires URL secrets to be cryptographically random, stored securely, single-use, and time-limited, without changing account state until the token is validated. An invitation is not a recovery token, but it has the same bearer-secret threat model until the recipient authenticates; this is an engineering inference from the guidance. [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

Application audit records should capture when, where, who, what, the affected object, outcome, and a correlation identifier. Administrative access, privilege changes, sensitive-data access, imports, and exports are specifically important events. Logs must be protected against unauthorized access and modification while excluding or masking secrets and unnecessary sensitive personal data. OWASP also identifies session-management interfaces used for support impersonation as privileged surfaces that require strong protection. [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

NIST privacy guidance favors data minimization, clear notice, granular administration, and selective disclosure proportionate to privacy risk. This supports generating an explicit redacted disclosure rather than exposing a live Case to an external recipient. [NIST SP 800-63A-4 privacy considerations](https://pages.nist.gov/800-63-4/sp800-63a/privacy/)

## Product-design inferences

The following choices are recommendations for AI OSINT Spider, not requirements stated verbatim by the cited standards.

### Identity boundary

- Keep local-only use accountless. Local database unlock and recovery are device concerns, not managed-account recovery.
- Use a stable person account for the managed service, with organization memberships and Case memberships as separate relationships. Organization administration must not silently grant Case-content access.
- Prefer passkeys for managed sign-in. Require a phishing-resistant method and recent user verification for organization owners and high-impact operations. Retain a password-plus-MFA compatibility path if needed.
- Encourage two passkeys or one passkey plus an offline saved recovery code. Do not let support staff bypass the documented recovery policy. Notify all established channels after recovery or authenticator changes and revoke existing sessions when risk calls for it.
- Treat Electron and mobile as public OAuth clients: open the system browser, use authorization code with PKCE, store refresh credentials in the OS-protected credential store, and never put managed credentials in a Case database.

### Authorization and roles

- Evaluate authorization as `principal -> organization membership -> Case membership -> action`, using current host-side state. Apply the same decision to the API, UI data, graph, search, artifact bytes, thumbnails, link previews, exports, agent jobs, event streams, and caches.
- Because the approved product rule makes all Case data, including sensitive data, visible to every user who has Case access, Case roles should govern actions rather than create hidden record-level visibility tiers.
- A practical starting split is organization Owner, Administrator, Billing Administrator, Auditor, and Member; and Case Owner, Manager, Investigator, Contributor, and Viewer. Service support has no standing Case-content role.
- Require recent reauthentication for authenticator changes, owner or administrator grants, ownership transfer, unredacted export, external sharing, permanent deletion, and enabling support access. Enterprise policy may require a second approver for selected destructive or disclosure actions, but routine investigation work should not require two-person approval.
- Prevent the last organization owner and last Case owner from leaving without a controlled transfer or recovery path. Periodically review memberships and elevated roles.

### Invitations and collaboration

- Bind an invitation to its organization, optional Case, intended role, inviter, intended recipient address, expiry, and one-time identifier. Store only a digest of its secret, make it revocable, and activate membership only after authenticated acceptance by the intended verified account.
- Exchange a link secret for an authenticated session immediately, then remove it from the visible URL and prevent it from reaching logs or referrers. Invitation messages should disclose as little Case information as possible.
- Record membership grants, role changes, removals, invitation acceptance, and rejected offline work in the Case history and security audit. Presence indicators and collaboration events do not substitute for authorization checks.

### Offline authorization and revocation

- Offline access to a managed Case cannot reflect a new revocation until the device reconnects or a previously issued authorization expires. Represent this honestly as a signed, device-bound offline authorization lease containing the account, organization, Case, allowed action class, policy or membership version, issued time, and expiry.
- Keep leases short enough for the Case risk profile, allow an organization to disable offline Case access, and use shorter or no offline grants for privileged actions. Membership changes, external sharing, permission grants, ownership transfer, and permanent deletion always require the authoritative host.
- When a lease expires, lock managed Case access and queued privileged mutations until reconnection. On reconnect, check current membership and policy before accepting each queued command; retain rejected user work as an explicit local draft when policy permits.
- A lease bounds future application access; it cannot erase information already viewed, copied, exported, photographed, or extracted from a compromised device. Product language must not promise instantaneous offline revocation or remote erasure.

### Support, audit, and redacted sharing

- Prefer scoped diagnostics and user-mediated support over impersonation. If impersonation remains available, require step-up authentication, an explicit time-limited Case grant, purpose and ticket, and a persistent banner. Preserve both the real administrator and effective user in every audit event, and notify the Case owner according to policy.
- Keep audit administration separate from ordinary organization administration where practical. Audit every privileged read and action, including audit-log access, but keep raw Case contents and credentials out of the security log.
- Make external sharing a version-bound, immutable redacted snapshot or a recipient-scoped derived view, never ambient access to the live Case. Allow-list included fields and renditions, process text, media metadata, thumbnails, previews, graph labels, and attachments through the same server-side disclosure policy, then show the sender a final preview and omission manifest.
- Give each share an audience, purpose, expiration, revocation control, and access/download history. A public bearer link is a weaker mode and should be visibly labeled as such. Watermarks and download controls deter redistribution but cannot guarantee confidentiality after disclosure.
