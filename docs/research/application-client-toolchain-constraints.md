# Application client toolchain constraints

Verified against official documentation and first-party source on 2026-10-25 for [Choose application architecture and build toolchain](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26). This is documentation research, not integration or packaging proof. No framework preference is an upstream fact.

## Project inputs

- The parent task fixes Electron on Windows and Linux, equal web and Electron features, and only usable mobile features. Accountless mobile Cases require encrypted persistence. Local SQLCipher, managed PostgreSQL and object storage, a TypeScript Connector SDK with a language-neutral bridge, no raw extension credentials, and npm 12 with the seven-day policy are approved inputs. Clients and the local runtime are open source. The managed backend remains private. These are supplied requirements, not conclusions from framework documentation. [Parent task](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26), [platform ADR](../adr/0001-local-first-clients-with-private-managed-cloud.md), [npm policy](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/23).

## Five constraints that affect the decision

1. Electron's renderer must remain a browser client with `sandbox: true`, `contextIsolation: true`, and `nodeIntegration: false`. Privileged work needs a restricted bridge. Enabling Node integration disables renderer sandboxing. [Electron sandbox](https://www.electronjs.org/docs/latest/tutorial/sandbox), [security guidance](https://www.electronjs.org/docs/latest/tutorial/security).
2. A static client and a runtime server are different deliverables. Vite normally emits static assets. Next.js static export omits runtime server features. A separate application host is therefore a project design obligation with either choice, not something static output supplies. The last sentence is a project inference. [Vite overview](https://vite.dev/guide/), [Next.js export limits](https://nextjs.org/docs/app/guides/static-exports#unsupported-features).
3. Expo Go cannot validate the proposed SQLCipher persistence. Expo's SQLCipher support requires native configuration and a rebuilt binary. An accepted `PRAGMA key` alone does not establish encryption. [Expo SQLite SQLCipher](https://docs.expo.dev/versions/latest/sdk/sqlite/#sqlcipher).
4. Windows and Linux support Android development, but local iOS native builds and the local iOS Simulator require a Mac. EAS can build iOS in the cloud from another operating system. Flutter retains the macOS requirement for local iOS builds. [React Native environment](https://reactnative.dev/docs/set-up-your-environment), [Expo Simulator](https://docs.expo.dev/workflow/ios-simulator/), [Expo development builds](https://docs.expo.dev/develop/development-builds/introduction/), [Flutter target setup](https://docs.flutter.dev/install/custom).
5. Standalone Node, npm, and Electron's embedded Node have separate compatibility constraints. Supported LTS lines today are Node 24 and 22. npm 12 imposes minimum versions within those lines, and dependency age checks do not approve native install scripts. [Node releases](https://nodejs.org/en/about/previous-releases), [npm engine declaration](https://raw.githubusercontent.com/npm/cli/latest/package.json), [npm install policy](https://docs.npmjs.com/cli/v12/commands/npm-ci/), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security).

## Shared React TypeScript web and Electron UI

- Source fact: Vite provides a development server, a React TypeScript template, and production static assets. It also supports SSR through separate server integration, so calling Vite universally client-only would be inaccurate. Its development server is not the application's production backend. [Vite overview](https://vite.dev/guide/), [Vite SSR](https://vite.dev/guide/ssr.html).
- Source fact: Next.js `output: 'export'` produces static HTML, CSS, and JavaScript. Server Components can execute at build time. Static export does not support Server Actions, request-dependent Route Handlers, request cookies, ISR, default image optimization, or dynamic route segments without predefined parameters. Client Components still prerender at build time, so browser APIs need browser-only access. [Next.js static export](https://nextjs.org/docs/app/guides/static-exports).
- Source fact: Next.js can operate as a runtime server when its server features are needed. That is a different deployment from static export. [Next.js deployment](https://nextjs.org/docs/app/getting-started/deploying), [Next.js server hosting](https://nextjs.org/docs/app/guides/self-hosting).
- Project inference: Vite is a candidate for one shared browser UI served on the web and packaged in Electron. Next.js is also a candidate if the common UI stays within static-export limits, or if a separately operated Next.js server is an intentional dependency. Export alone cannot supply offline request-time server behavior. [Vite overview](https://vite.dev/guide/), [Next.js static export](https://nextjs.org/docs/app/guides/static-exports).
- Project inference: Domain contracts and application behavior can live outside either framework. Browser transport, Electron IPC, local SQLCipher access, and managed API access need host-specific adapters. Web parity requires the compatible local runtime for native capabilities, as the ADR permits. Framework routes must not become the only implementation of shared Case behavior. [Platform ADR](../adr/0001-local-first-clients-with-private-managed-cloud.md), [Electron sandbox](https://www.electronjs.org/docs/latest/tutorial/sandbox).
- Untested packaging: Neither framework's documentation proves this project's routing, asset URLs, custom Electron protocol, CSP, offline behavior, or local-host authentication. Bundling a Next.js runtime server adds startup, shutdown, updates, and port ownership to the proposed packaging. These remain project questions. [Electron protocol guidance](https://www.electronjs.org/docs/latest/tutorial/security#18-avoid-usage-of-the-file-protocol-and-prefer-usage-of-custom-protocols), [Next.js hosting](https://nextjs.org/docs/app/guides/self-hosting).

## Electron security and runtime boundaries

- Source fact: Electron recommends context isolation in every renderer, process sandboxing, restrictive CSP, secure content, restricted navigation and new windows, and IPC sender validation. Remote code must never run with Node integration enabled. The settings above express this project's security baseline, not a claim that Electron prevents every unsafe configuration. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security).
- Source fact: Sandboxed renderers have no Node environment. Sandboxed preload scripts have restricted capabilities and are more privileged than page scripts. `contextBridge` can expose a separate method for each permitted operation. Exposing arbitrary IPC forwarding bypasses that restriction. [Electron sandbox](https://www.electronjs.org/docs/latest/tutorial/sandbox), [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation).
- Project inference: SQLCipher, filesystem access, Connector execution, and secret access belong behind privileged host APIs. The renderer and extensions receive permitted operations, not raw credentials or generic filesystem, shell, or IPC access. A module boundary lint rule does not sandbox a Connector. [Parent credential constraint](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26), [Electron bridge guidance](https://www.electronjs.org/docs/latest/tutorial/context-isolation), [sandbox privilege model](https://www.electronjs.org/docs/latest/tutorial/sandbox).
- Source fact: Electron ships its own Chromium and Node. Native Node modules may require rebuilding against Electron's ABI. Updating a separately installed Node LTS does not update Electron's embedded runtime. [Electron bundled components](https://www.electronjs.org/docs/latest/tutorial/security), [native module ABI](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules).
- Project inference: Build tooling and a separately executed local host may use standalone Node LTS. A host running inside Electron instead uses Electron's embedded runtime. SQLCipher native binaries must match the chosen process, operating system, and architecture. Neither deployment arrangement has been established here. [Electron native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules).

## Mobile alternatives and encrypted local Cases

- Source fact: React Native uses React to create native Android and iOS views. Its usual JavaScript runtime is Hermes, not the standalone Node process used by development tools. Shared React knowledge does not make a DOM component a native component. The last sentence is an inference from the rendering model. [Native components](https://reactnative.dev/docs/intro-react-native-components), [JavaScript environment](https://reactnative.dev/docs/javascript-environment).
- Project inference: Expo React Native can reuse platform-independent TypeScript contracts and domain logic, provided those packages avoid DOM, Electron, and Node dependencies. Mobile still needs appropriate screens, native storage adapters, and the approved language-neutral bridge for host capabilities. Direct mobile execution of a Node-dependent Connector SDK is unsupported by this research. [React Native runtime](https://reactnative.dev/docs/javascript-environment), [parent SDK constraint](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26).
- Source fact: Expo development builds permit custom native libraries and configuration. Expo Go permits only its included native libraries and libraries without additional native code. Adding or changing native code requires another native build. Development builds may compile locally or through EAS. [Expo native code](https://docs.expo.dev/workflow/customizing/), [development builds](https://docs.expo.dev/develop/development-builds/introduction/).
- Source fact: `expo-sqlite` documents SQLCipher on Android and iOS through `useSQLCipher` and native prebuild. Expo Go does not support SQLCipher. Without SQLCipher in the binary, SQLite silently ignores `PRAGMA key`. Expo documents `PRAGMA cipher_version` as an availability check. This is documented support, not proof of a working application build. [Expo SQLCipher](https://docs.expo.dev/versions/latest/sdk/sqlite/#sqlcipher).
- Source fact: Expo SecureStore stores Android values encrypted using Android Keystore and iOS values in Keychain. Android restored backups cannot decrypt entries after uninstall removes the keys. iOS Keychain values can survive reinstall. [SecureStore storage and backup](https://docs.expo.dev/versions/latest/sdk/securestore/).
- Project inference: Accountless local Cases need encrypted database and Artifact persistence, key lifecycle, deletion, and recovery rules independent of managed login. SecureStore is a candidate for small key material. SQLCipher support alone does not establish encrypted external Artifact files, recoverable backups, or safe temporary files. [Parent mobile constraint](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26), [SQLCipher scope](https://docs.expo.dev/versions/latest/sdk/sqlite/#sqlcipher), [SecureStore lifecycle](https://docs.expo.dev/versions/latest/sdk/securestore/).
- Source fact: Flutter uses Dart and its own widget framework, with platform channels and FFI for native integration. Android development is available across host operating systems. Local iOS development requires macOS and Xcode. [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview), [platform channels](https://docs.flutter.dev/platform-integration/platform-channels), [target setup](https://docs.flutter.dev/install/custom), [iOS setup](https://docs.flutter.dev/platform-integration/ios/setup).
- Project inference: Flutter remains a mobile alternative with separate Dart UI and domain bindings to the language-neutral protocol. It does not reuse the shared React TypeScript UI directly. Choosing Flutter does not resolve encrypted database packaging or key management. No Flutter SQLCipher binding is selected or validated in this note. [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview), [parent protocol and storage constraints](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26).
- Source fact: EAS cloud builds can produce iOS binaries from any development OS. The local iOS Simulator remains macOS-only. A cloud build does not provide a local Windows or Linux iOS Simulator. Expo also documents remote simulator access as a separate option. [Expo development builds](https://docs.expo.dev/develop/development-builds/introduction/), [Simulator requirements](https://docs.expo.dev/workflow/ios-simulator/).

## Node, npm workspaces, TypeScript, and lint boundaries

- Source fact: Node 24 and 22 are LTS on the verification date. Node 26 is Current and Node 20 is EOL. Node recommends Active or Maintenance LTS for production. These labels concern standalone Node, not Electron's embedded version. [Node releases](https://nodejs.org/en/about/previous-releases), [Electron components](https://www.electronjs.org/docs/latest/tutorial/security).
- Source fact: npm 12's current engine declaration accepts sufficiently recent Node 22 and 24 releases and Node 26 or newer. Therefore, arbitrary old releases within an LTS major are not interchangeable. Exact engine floors belong to the selected npm release, not a permanent patch pin in this decision. [npm engine declaration](https://raw.githubusercontent.com/npm/cli/latest/package.json).
- Source fact: npm workspaces link declared local packages and run commands within selected workspaces. Expo documents npm workspace support, but warns against duplicate React Native versions and conflicting native modules. Workspace support does not prove compatibility of every package combination. The last sentence is a project inference. [npm workspaces](https://docs.npmjs.com/cli/v12/using-npm/workspaces/), [Expo monorepos](https://docs.expo.dev/guides/monorepos/).
- Source fact: npm 12's `min-release-age=7` filters dependency resolution by days since publication and errors when no eligible version exists. Exclusions and higher-priority configuration can change the policy. `npm audit fix` can retain a vulnerable version and exit nonzero when the gate blocks its fix. [npm configuration](https://docs.npmjs.com/cli/v12/using-npm/config/#min-release-age).
- Source fact: npm 12 controls dependency lifecycle scripts separately through approvals. `strict-allow-scripts` rejects unreviewed scripts. Directory dependency controls also exist, so an indiscriminate ban on local directories needs review alongside workspace links. [npm install policy](https://docs.npmjs.com/cli/v12/commands/npm-ci/), [directory controls](https://docs.npmjs.com/cli/v12/using-npm/config/#allow-directory), [workspace links](https://docs.npmjs.com/cli/v12/using-npm/workspaces/).
- Project inference: The approved npm policy applies to Vite, Next.js, Expo, Electron tooling, and their native dependencies. Download or compile steps need reviewed script approvals. A framework's suggested bootstrap command is not an exception. Compatibility with the actual policy and cloud build image remains untested. [Existing npm policy](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/23), [npm approvals](https://docs.npmjs.com/cli/v12/commands/npm-ci/).
- Source fact: Vite transpiles TypeScript without type checking. Type checking can run separately with `tsc --noEmit`. TypeScript project references and `tsc -b` can build referenced projects in dependency order. These mechanisms do not package Electron or compile mobile native code. The last sentence is an inference about their documented scope. [Vite TypeScript](https://vite.dev/guide/features.html#typescript), [TypeScript references](https://www.typescriptlang.org/docs/handbook/project-references.html).
- Source fact: ESLint 10 requires flat configuration. Current typescript-eslint documents ESLint 9 and 10 support and TypeScript support below 6.1, including 6.0. Plugin and parser ranges must be considered together. [ESLint migration](https://eslint.org/docs/latest/use/migrate-to-10.0.0), [typescript-eslint compatibility](https://typescript-eslint.io/users/dependency-versions/).
- Source fact: JS Boundaries documents `eslint-plugin-boundaries`, flat configuration, and compatibility with ESLint 9 and above. Its repository describes rules for allowed architectural dependencies. This makes it a candidate for import constraints, not runtime isolation. [Installation](https://www.jsboundaries.dev/docs/installation/), [plugin source documentation](https://github.com/javierbrea/eslint-plugin-boundaries).
- Untested packaging: The cited plugin installation page names `eslint-plugin-boundaries`, while the inspected v7 source package names `@boundaries/eslint-plugin`. Published artifact identity, resolver behavior, and the chosen ESLint combination need confirmation before adoption. Neither a broad peer range nor documentation proves that this repository's aliases and type-only imports are covered. [Installation page](https://www.jsboundaries.dev/docs/installation/), [tagged package metadata](https://raw.githubusercontent.com/javierbrea/eslint-plugin-boundaries/v7.2.0/packages/eslint-plugin/package.json).

## Unsupported assumptions

- This research does not establish that Vite or Next.js is preferable, that Electron packages work on Windows and Linux, or that export-mode routing preserves all Case workflows. It identifies constraints for a later decision. [Vite build model](https://vite.dev/guide/), [Next.js export limits](https://nextjs.org/docs/app/guides/static-exports), [Electron native ABI](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules).
- Direct DOM UI reuse on mobile, Node-dependent Connector execution on mobile, encrypted Artifact files from SQLCipher alone, automatic accountless recovery, and complete npm-policy compatibility on EAS are unproven. No installation, implementation, native build, test, or integration validation was performed. [React Native components](https://reactnative.dev/docs/intro-react-native-components), [runtime](https://reactnative.dev/docs/javascript-environment), [SQLCipher scope](https://docs.expo.dev/versions/latest/sdk/sqlite/#sqlcipher), [SecureStore lifecycle](https://docs.expo.dev/versions/latest/sdk/securestore/), [EAS build service](https://docs.expo.dev/build/introduction/).
