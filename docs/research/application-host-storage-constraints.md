# Application host and storage constraints

Verified against official documentation and first-party source on 2026-10-25 for [Choose application architecture and build toolchain](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26). This is documentary research. No packages, builds, runtime behavior, or integration have been qualified. Links to `latest` and development branches describe the material inspected, not selected dependency versions.

## Approved context

Project inputs, not conclusions from vendor documentation: Electron on Windows/Linux is fixed; web and Electron need the same feature set; mobile includes only usable features and accountless local Cases require encrypted persistence. Local SQLCipher and managed PostgreSQL/object storage are approved. Clients and local runtime remain open source; the managed backend stays private. The TypeScript Connector SDK needs a language-neutral bridge, extensions receive no raw credentials, and the Node runtime choice plus npm 12 seven-day dependency safety policy are already approved. This note does not reopen those decisions. [Parent decision](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26), [ADR 0001](../adr/0001-local-first-clients-with-private-managed-cloud.md), [Connector constraints](connector-sdk-execution-constraints.md), [dependency policy research](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/23)

## Host choices

Source facts: Fastify uses Ajv for request validation and fast-json-stringify for schema-based response serialization. It compiles schemas using `new Function()` and explicitly treats schemas as application code, unsafe when supplied by users. Response schemas help prevent accidental sensitive-field disclosure. Database work during initial asynchronous validation can enable denial of service; Fastify recommends a later hook such as `preHandler`. [Fastify validation and serialization](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

Project inference: a shared TypeScript Domain and application layer in a Node/Fastify process is the preferred candidate under the TypeScript SDK constraint. Keep product rules independent of HTTP, Electron, and native storage. Ship reviewed request/response schemas; never compile imported Case content or extension-supplied schemas as trusted application schemas. Parse requests before authorization and application work, and authorize every operation independently of schema validity. This is a design recommendation, not a measured performance advantage. [Fastify constraints](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/), [Connector authorization constraints](connector-sdk-execution-constraints.md)

Source facts: Node supplies filesystem operations and OpenSSL-backed cryptography. Concurrent promise-based modifications of the same file are not synchronized and may corrupt data. Its permission model prevents accidental access by trusted code but explicitly provides no guarantee against malicious code. Native addons need explicit permission when that model is enabled. [Node filesystem](https://nodejs.org/api/fs.html#promises-api), [Node crypto](https://nodejs.org/api/crypto.html), [Node permissions](https://nodejs.org/api/permissions.html)

Project inference: Node can perform ordinary file and cryptographic work; moving all such work to Rust is unnecessary. A narrow Rust sidecar is a candidate for SQLCipher ownership, OS credential-store access, and platform process controls that need native bindings. Give it versioned, validated commands and explicit lifecycle handling. Keep Case rules in TypeScript and trust neither Node permission flags nor the mere existence of a second process as extension containment. [Node permissions](https://nodejs.org/api/permissions.html), [platform isolation constraints](connector-sdk-execution-constraints.md)

Source facts: Rust's process API inherits environment variables and, for `spawn`, standard streams by default. Rusqlite is a wrapper around SQLite's native C API, not an OS confinement mechanism. [Rust Command](https://doc.rust-lang.org/std/process/struct.Command.html), [rusqlite and libsqlite3-sys](https://github.com/rusqlite/rusqlite#notes-on-building-rusqlite-and-libsqlite3-sys)

Project inference: a Rust core could own the application rules and native storage together, but sharing those rules with TypeScript clients would then require a qualified bridge or a separate browser/WASM design. This widens the work beyond a narrow platform sidecar. Rust, rusqlite, filtered environments, and process separation do not automatically create an OS sandbox. Actual filesystem, network, descendant-process, and credential isolation still needs explicit platform enforcement. [Rust process defaults](https://doc.rust-lang.org/std/process/struct.Command.html), [existing isolation findings](connector-sdk-execution-constraints.md), [web/Electron constraint](../adr/0001-local-first-clients-with-private-managed-cloud.md)

Source facts: FastAPI uses Python type declarations and Pydantic for data validation and requires an ASGI server such as Uvicorn to serve requests. [FastAPI data handling](https://fastapi.tiangolo.com/features/), [FastAPI deployment](https://fastapi.tiangolo.com/deployment/manually/)

Project inference: a Python/FastAPI core is viable as an HTTP host, but it adds Python runtime distribution and a boundary to the required TypeScript SDK. Pydantic models do not themselves share executable TypeScript Case rules. Prefer Python for selected bridged workers unless its application-level benefit justifies moving Domain ownership. Neither the Rust nor Python alternative has a demonstrated packaging, security, or throughput advantage here. [FastAPI deployment model](https://fastapi.tiangolo.com/deployment/manually/), [FastAPI validation model](https://fastapi.tiangolo.com/features/), [parent constraints](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/26)

## Desktop native storage and packaging

Source facts: rusqlite offers `sqlcipher` for linking an installed SQLCipher library, `bundled-sqlcipher` for compiling bundled SQLCipher with a system crypto provider, and `bundled-sqlcipher-vendored-openssl` for also building OpenSSL. `sqlcipher` overrides ordinary `bundled`; ordinary bundled SQLite does not select encryption. `libsqlite3-sys` provides the native bindings and build logic. [rusqlite build options](https://github.com/rusqlite/rusqlite#optional-features), [libsqlite3-sys features](https://github.com/rusqlite/rusqlite/blob/master/libsqlite3-sys/Cargo.toml)

Source facts: the inspected build script contains Windows-specific OpenSSL discovery/linking and a vendored-OpenSSL path, while retaining a warning describing bundled SQLCipher as Unix-only. It also sets `SQLITE_ENABLE_FTS5` for bundled builds. These source paths are evidence of build mechanisms, not qualification of every Windows/Linux target. Vendored OpenSSL requires native build tools, including a C compiler, Perl, and make, according to its binding documentation. [libsqlite3-sys build script](https://github.com/rusqlite/rusqlite/blob/master/libsqlite3-sys/build.rs), [OpenSSL vendored build](https://docs.rs/openssl/latest/openssl/#vendored)

Source facts: Node-API stabilizes its own ABI, but external native libraries and other Node/V8 APIs may not share that guarantee. Electron documents a different native-module ABI from standalone Node and rebuilding modules for Electron. [Node-API ABI limits](https://nodejs.org/api/n-api.html#implications-of-abi-stability), [Electron native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules)

Untested packaging implication: a separately executable Rust SQLCipher sidecar avoids loading that binding into Electron's native-module ABI. It still needs pinned Rust/C/OpenSSL inputs and qualification on each supported Windows/Linux architecture and Linux runtime baseline. Confirm crypto linkage, shipped libraries/notices, SQLCipher version, encrypted reopen, wrong-key failure, FTS5 availability, upgrades, and recovery. No feature flag or upstream source branch proves the resulting installer works. [Native build inputs](https://github.com/rusqlite/rusqlite#notes-on-building-rusqlite-and-libsqlite3-sys), [ABI constraints](https://nodejs.org/api/n-api.html#implications-of-abi-stability)

## Mobile encrypted local Cases

Source facts: Expo SQLite documents SQLCipher on Android and iOS, enabled with `useSQLCipher` and a native prebuild/rebuild. SQLCipher is unavailable in Expo Go. `enableFTS` controls FTS3/4/5 and defaults to true. Ordinary SQLite silently ignores `PRAGMA key`; Expo recommends checking `PRAGMA cipher_version` before setting the key. Expo's SQLCipher platform list does not include web. [Expo SQLite configuration and SQLCipher](https://docs.expo.dev/versions/latest/sdk/sqlite/)

Project inference: native Expo SQLCipher is a candidate for accountless mobile Cases; it does not establish browser SQLCipher. Fail closed when encryption is absent. Qualify FTS5 creation, insert/query, encrypted reopen, and migration in the actual iOS/Android SQLCipher binaries. Separate configuration switches and examples do not prove their combined release behavior. Select native key custody and recovery explicitly; no hardcoded example password is acceptable. [Expo build and encryption caveats](https://docs.expo.dev/versions/latest/sdk/sqlite/)

Source fact: SQLCipher encrypts database pages and journal/WAL page data, but other temporary files may remain unencrypted; Zetetic requires disabling file-backed temporary storage where used. Project inference: database encryption does not cover external Artifact bytes, exports, thumbnails, logs, or key backups. Accountless mobile encrypted persistence needs a design for each retained copy, not just a database option. [SQLCipher design](https://www.zetetic.net/sqlcipher/design/), [storage constraints](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/15)

## Transaction ports and engine differences

Source facts: node-postgres exposes transactions through explicit `BEGIN`, `COMMIT`, and `ROLLBACK`, with every statement using the same checked-out client. Rusqlite exposes a transaction bound to a connection, with rollback by default and explicit commit. These are usable low-level transaction mechanisms. [node-postgres transactions](https://node-postgres.com/features/transactions), [rusqlite Transaction](https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html)

Source facts: SQLite normally provides serializable isolation by serializing writes, with one writer at a time; shared-cache/read-uncommitted configuration is an exception. PostgreSQL defaults to Read Committed with statement snapshots, and its Serializable transactions can abort and require whole-transaction retry. SQLCipher uses SQLite's API. Identically named transaction wrappers therefore do not imply identical concurrency behavior. [SQLite isolation](https://www.sqlite.org/isolation.html), [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [SQLCipher design](https://www.zetetic.net/sqlcipher/design/)

Project inference: define application-owned storage ports around Case operations and transaction scope, with separate PostgreSQL and SQLCipher SQL/migrations. Keep raw SQL and transaction handles inside trusted adapters; extensions must not receive arbitrary SQL execution. An ORM/query builder may reduce mapping work, but cannot establish portable isolation, retry, locking, search, typing, or migration semantics. Avoid a shared generic SQL API that hides those differences. [Driver transaction requirements](https://node-postgres.com/features/transactions), [engine differences](https://www.postgresql.org/docs/current/transaction-iso.html), [SQLite isolation](https://www.sqlite.org/isolation.html), [extension boundary](connector-sdk-execution-constraints.md)

Untested integration implication: one local transaction must remain on the sidecar's owned connection across the complete application operation. Per-statement bridge calls without transaction identity/lifetime are insufficient. Database commit also cannot establish atomicity with separately stored Artifact bytes or managed object storage; recovery needs its own protocol. [Connection-bound transactions](https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html), [Artifact consistency constraints](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/15)

## Browser access to the local host

Source facts: Chrome introduced permission-gated Local Network Access in 142, split local-network and loopback-network permissions in 145, and extended restrictions to WebSocket/WebTransport in 147. The permission requires a secure context. This supersedes the old Private Network Access preflight approach. The current WICG document is a community draft, not proof of browser interoperability. [Chrome release notes](https://support.google.com/chrome/a/answer/10314655?hl=en-en-4), [LNA draft](https://wicg.github.io/local-network-access/)

Source facts: Google's current guidance requires permission plus normal CORS handling for reading cross-origin responses and documents mixed-content constraints. The LNA draft exempts potentially trustworthy same-origin requests; secure-context rules recognize loopback IP origins as potentially trustworthy. [Chrome LNA guidance](https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/security/local-network-access.md), [LNA request algorithm](https://wicg.github.io/local-network-access/#local-network-access-check), [secure-context origin rules](https://www.w3.org/TR/secure-contexts/#is-origin-trustworthy)

Project inference: prefer serving the accountless browser UI and API from the same loopback scheme/host/port, with the local runtime owning SQLCipher and native execution. This fits web/Electron feature parity without making hosted HTTPS-to-loopback requests the only local entry. A hosted HTTPS UI talking directly to loopback is a separate pairing mode requiring permission-denied UX, CORS, and browser qualification. Firefox, Safari, enterprise policy, and exact shipped-browser behavior remain unverified; do not infer compatibility from Chrome documentation. [Product boundary](../adr/0001-local-first-clients-with-private-managed-cloud.md), [same-origin exception](https://wicg.github.io/local-network-access/#local-network-access-check), [Chrome guidance](https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/security/local-network-access.md)

Source facts: MCP's HTTP transport requires Origin validation and recommends localhost binding plus authentication. Its Fastify adapter separately documents Host allowlists for DNS-rebinding protection. Those are MCP requirements/examples, not automatic guarantees of an arbitrary Fastify application. [MCP transport security](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#security-warning), [MCP Fastify Host validation](https://ts.sdk.modelcontextprotocol.io/v2/api/@modelcontextprotocol/fastify/fastify.html)

Project inference: apply equivalent defenses to this local host. Bind explicitly to loopback; allowlist Host and exact approved browser origins; reject invalid origins on HTTP and WebSocket upgrades; protect mutations against CSRF. Pair the intended browser with a short-lived local authorization ceremony and revocable session before granting Case/native authority. Browser network permission alone grants no Case authorization. Accountless still needs local authentication, and no raw extension credentials may enter the browser or worker bridge. The precise pairing protocol remains undesigned. [Local transport threat model](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#security-warning), [Host validation example](https://ts.sdk.modelcontextprotocol.io/v2/api/@modelcontextprotocol/fastify/fastify.html), [credential policy](connector-sdk-execution-constraints.md)

## Decision boundary

Recommendation, not integration proof: carry forward TypeScript Domain/application ownership, a Node/Fastify host, narrow native Rust responsibilities, and engine-specific storage adapters. Retain Rust-core and Python-core alternatives only if later qualification identifies a concrete requirement the narrower arrangement cannot meet. The evidence above establishes constraints; it supplies no benchmark or completed integration. [Host/schema limits](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/), [native build options](https://github.com/rusqlite/rusqlite#notes-on-building-rusqlite-and-libsqlite3-sys), [FastAPI host model](https://fastapi.tiangolo.com/deployment/manually/)

Material uncertainties remain: the pinned desktop SQLCipher/OpenSSL package matrix; real mobile SQLCipher+FTS5 builds and key recovery; transaction lifetime/cancellation across the sidecar; Artifact/database crash consistency; explicit Windows/Linux extension containment; and paired browser behavior across supported versions. These are qualification gates for the parent decision, not work performed or support promised by this research. [Native build caveats](https://github.com/rusqlite/rusqlite/blob/master/libsqlite3-sys/build.rs), [mobile configuration](https://docs.expo.dev/versions/latest/sdk/sqlite/), [transaction ownership](https://docs.rs/rusqlite/latest/rusqlite/struct.Transaction.html), [storage limitations](https://github.com/TheDarkSkyXD/OSINT-AI-Spider/issues/15), [isolation limitations](connector-sdk-execution-constraints.md), [browser permission model](https://wicg.github.io/local-network-access/)
